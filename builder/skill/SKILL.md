# Build a phone agent from a bank's case material

You work alone in the current folder, and it holds everything you need: the case material under `inputs/` (a brief file, or the folder `inputs/case/` with the bank's documents) and the tool API file `inputs/openapi.json` when there is one, `docs/`, `examples/base-agent.json`, `freya.py`, the tested helpers in `lib/`, and the checkers in `tools/`.
Nobody is available to answer questions, so decide from the brief and keep going. The case material and the tool API file are your only source of facts: every number, date, name and rule in the agent comes from them. "The brief" below means all of the case material.
You have a fixed time budget (in the prompt). Save a working agent early, then improve it.

The current case is the specification. The patterns below are conditional implementation guidance, not a required collection workflow: add only stages, checks, data disclosures, actions and outcomes supported by the current case material and tool contract. Do not carry behavior over from a practice case merely because it appears in an example below.

## The idea

A phone call is a chain of small steps. Let **code** decide everything that can be computed (dates, bands, deadlines, counters, outcomes) and let the **model** do only what needs language: talk, listen, hand back the customer's words. Give the model one finished fact at a time and one job per step.

The call starts on a passthrough code node (the initial node) that sets the first sentence and leads to a talk node whose fixed text is `{{say}}`; an initial conversation node with an `always` transition hangs the call (seen live: 60 s timeouts, no call ever started).

Bank tools are never called by the model. Each one runs in an `api_request` node (`pre_actions`) and every argument comes from a variable that code set (`"default": "{{v_field}}"`). A model that is left to fill a tool's arguments can leave them out, and then every call fails (seen live: `verify_identity` called with only the customer id, three calls out of three). If the current case requires a workflow-level tool, set its arguments from code as well.

## Steps

1. Read the case material. For a folder, read EVERY file: Markdown and text as they are, a `.docx` or `.xlsx` through its converted `.txt` or `.csv` copy next to it, a PDF with the Read tool. Different documents can cover different parts (the policy, the flow, announcements, the service contract, test customers, questions and answers); put each rule in the spec with the file it came from. Where a later announcement or memo changes an earlier rule, the later one wins; note each such conflict in the spec. Example conversations show wording, tone and typical customers only; the rules come from the documents. If the brief says it builds on or refers to another brief ("Every rule of Brief A applies"), the other brief is in `inputs/related/`: read it and build the complete agent from both, the referring brief's rules replacing the other's where it says so. Read the tool API file (when there is none, take the tools, their paths, fields and every allowed value from the documents; the API checks are then skipped, so copy names and allowed values exactly), `docs/workflow-format.md`, `docs/tools-and-code.md` and `examples/base-agent.json` (a pattern for the JSON).
2. Write `out/spec.json`: every applicable constant the brief fixes, each with its rule number: for example, bands and limits, business-day counts, holidays, working days, time windows, attempt counts, floors, fixed sentences, outcome/reason mappings and queue names when the case defines them. Do not invent a constant or include an irrelevant category. Where the brief is unclear, take the literal reading and mark the entry `"unclear": true`.
3. Write `out/gen.py`. It reads `out/spec.json` and the tool API file and writes `out/<slot>.workflow.json` (`<slot>` is in the prompt). A constant lives in the spec once; the generator writes it everywhere it is needed. Tool URLs, fields and allowed values come from the tool API file. When the prompt names a base URL for the bank, every tool call goes to that URL (`<base URL>` + the tool's path) and to no other host.
4. Build the code nodes from `lib/`. `lib/cal.py` holds tested functions; `from snippets import code` (after `sys.path.insert(0, "lib")`) gives `code(body, spec_subset)`, the text of a code node that already contains `SPEC` and every helper:
   `parse_now`, `to_date`, `is_bd`, `add_bd` (the n-th business day after a date), `on_or_after_bd`, `last_bd_of_week`, `say_date`, `resolve_phrase(text, today, next_week_mode)` (customer words to a date), `hhmm_from_words`, `promise_date_state`, `callback_state`, `band_for`, `floor_for`. Read the docstrings in `lib/cal.py`. The helper text is about 9 KB: put `code(...)` only into the few code nodes that call a helper (date facts, date and time checks), and keep closing nodes as short plain snippets without it. Check that the brief's meaning of "this/next weekday", "business day" and "later than now" matches the helper; if it differs, write the variant in the spec and the body.
5. Shape the agent with these patterns:
   - **Language.** Find the language of the case: the documents and especially the example conversations. The agent speaks that language in every sentence it says: the opening, the questions, the failure sentence ("there was a technical problem, I will try once more"), the offers, the read-back, the goodbye, and the node prompts' fixed sentences. Take fixed sentences from the documents when they give them; otherwise write them in the case language with the register the example conversations use (formal or informal address). Turkish writes a time as 15.30, an amount as 1.250,50 and a date as 15.11.2026 (day first); the Turkish helpers read these forms. Extraction fields hold the customer's words as text in that language, and `lib/cal.py` has Turkish helpers for those words (`resolve_phrase_tr`, `hhmm_from_words_tr`, `numbers_tr`, `digits_tr`, `amount_tr` ("1.250,50", "bin iki yüz elli lira" -> float), `say_amount_tr` (1250.5 -> "1.250,50 TL"), `say_date_tr`, and `resolve_phrase_any(text, today, lang)` / `hhmm_from_words_any` / `say_date_any` for a language switch). For another language, write the same helpers in the node's own code from the documents' words for days, months, numbers and parts of the day, and test them in `out/scenarios.json`. Keep identifiers, enum values and tool fields exactly as the tool API gives them (they are not translated).
   - **Opening:** the brief's required first sentence as a fixed `tts` `on_enter` text, word for word (except the recording wording in the next point). Follow the case's stated verification boundary; do not add an identity check when the case says a trusted upstream step has already completed it.
   - **Recording notice:** when the brief says the call is recorded without giving the exact sentence in quotation marks, say it in the case language as "we are recording this call" (Turkish: "bu görüşme kaydediliyor") and avoid the word for "recorded" in your own wording: a test judge may flag "recorded" said before a successful tool call (measured 3/3 with "recording" against 1/3 to 2/3 with "recorded"). A sentence the brief gives in quotation marks stays word for word. After a failed tool say "there was a technical problem, I will try once more"; say a promise or note is recorded ("kaydedildi" in Turkish) only after the result says `ok: true`; the same holds for every claim about what was done.
   - **Computed facts:** when the case defines calculations, compute them in code from the case data and call's `now`; give the model the finished facts it needs, not a task to calculate them.
   - **Customer's dates and times:** when a case flow accepts dates or times, keep the customer's words as text, resolve them from the call's `now` with the appropriate helper, and check them against the case rules before acting. When the words give no date or time, ask for the missing detail.
   - **Counters in code:** implement only counters and one-time limits required by the case. A route moves the call forward on a code or tool result.
   - **Extraction variables take only their listed values.** A code node that writes anything else to them (for example `''` to clear one) is rejected by the platform and the old value stays, so the next route sees a stale value. Give every extraction enum a neutral value such as `none` and reset to it. `tools/validate.py` reports every such write.
   - **Count each event in exactly one place.** A refusal, a human request or an unclear answer is counted either by a global (intent) node or by the step's own route, never by both. When a global node covers an event, list in its `excluded_nodes` every step that handles that event itself, including that step's counting node. Otherwise one customer sentence is counted twice (seen: one "I don't care" counted as two refusals and ended the call).
   - **Global (intent) nodes see every transition.** A global node is checked after each route, so one customer sentence can fire it again while a code node runs, and the node then returns to the previous node, which re-runs its counter. Put every non-conversation node (code, api request, end) and every step that handles the event itself in the global node's `excluded_nodes`. Handle the same event in a step that the global node excludes (for example the opening step) with its own enum value, so it is never lost.
   - **A question is not a refusal.** Give customer questions ("is this a scam?", "who is this?", "what is this about?") their own enum value, answer them with the brief's sentence, and ask again; only a real refusal moves a counter.
   - **Each extraction value maps to one rule of the brief.** Describe each value by what the customer says, and give requests the brief answers with a refusal (a discount, a waiver, a lower price) their own value or `other`, answered with the brief's sentence. A request must never be routed to a transfer or a close unless the brief says so for exactly that request.
   - **Cover everything the data can contain.** If `get_account` can return several items (products, accounts, appointments), the agent handles every one of them in the order the tool returns them, with its own counters and facts per item. Read the brief for how items combine in the read-back, the recording and the closing.
   - **Lists from a tool are mapped one field at a time.** The platform stores single values only, so a `response_mapping` path that points at a list (`data.products`) leaves the variable empty (seen live: every call ended as a service error). Map each field of item 0, 1, 2 ... with flattened paths (`data.products.0.past_due` into `p0_past_due`, `data.products.1.past_due` into `p1_past_due`, up to 6 items) and rebuild the list in code with `items_from_vars(vars, [field names])`. The platform also stores every response list as flattened variables named `<node>_response.data.<list>.<i>.<field>` whatever you map; `items_from_keys(vars, 'products')` rebuilds the list from those and is the safer reader (use it in the code that reads the list).
   - **A tool failure is not a wrong answer.** When `verify_identity` or `get_account` fails (no `ok`, an error), retry once as the brief says, then close with the brief's service-error outcome. Count a wrong answer only when the tool answered `verified: false`.
   - **Once-only offers:** each gets its own node whose entry is the fixed sentence; the route then moves on, so the sentence is said once.
   - **Numbers the customer says in words come from the extraction model as digits.** When the case needs numeric values from speech, use numeric extraction fields and read them with `num_of(v)` from `lib/cal.py`, never with a bare `int(v)`: extracted values can contain stray prefixes. Use `numbers_tr`, `digits_tr`, or `amount_tr` only to repair a field the model left as text. Validate dates and numeric ranges against the current case and API; do not add fixed bounds that the sources do not specify.
   - **Identity:** when the case requires a verification tool, call it only with a complete answer in the API's format. If the customer gives a partial answer, ask for the missing part, then call. Apply only the case's wrong-answer and retry rules.
   - **Requests that the brief answers apply in every stage.** Handle cross-stage requests and questions wherever they can occur, exactly as the case says. Do not add request types, persuasion steps or transfers that the case does not specify. No stage may leave an action request to the talk model to invent; route it through code and the required tool.
   - **One sentence can carry several things.** Extract every signal relevant to the current step: the answer to the pending question, details needed for an action, the requested action, and any side question. Follow priority rules in the case documents; never let a side question or broad intent label erase a specific answer or required action detail. Do not impose a priority between signals unless the case defines it.
   - **The talk node says the given text and nothing else.** Its prompt must say: "Say exactly this text. Never promise a transfer, a callback or any other action that the text does not state." The code decides what happens; the talk node only speaks.
   - **Answers that arrive in pieces:** when a case requires a multi-part answer, keep provided parts in code variables, merge new parts after each turn, and call the relevant tool only when the answer is complete. Ask only for the missing part. Follow the case rules for incomplete answers, retries and refusals.
   - **Closing:** when the case contract defines a closing/reporting tool, derive its outcome and reason in code from the call's state and invoke it at the point and with the arguments required by the contract. Do not invent a closing tool or outcome scheme when the case does not define one.
   - **The model never writes tool arguments.** Set every required action and closing argument from code variables or fixed API values. Use the supplied pre-process helpers when they match the contract; otherwise follow the contract's exact fields, allowed values and failure behavior.
   - **Once means once, across every trigger.** When the case limits an offer, question or action to one occurrence, track it with one code counter across all routes that can trigger it. Process the customer's answer to a pending offer before handling any additional request in the same turn.
   - **Wording limits count the closing lines too.** When the brief limits a wording ("one short sentence of sympathy", "say it once"), every fixed sentence of the agent counts, goodbyes included: after a sympathy sentence the goodbye is plain (no second "get well soon", "I am sorry"), and a side question from the customer ("am I talking to a robot?") is answered in the same turn as the rest of what they said, not skipped (seen: a customer asked "is this a robot?" while giving a date and the agent only handled the date).
   - **A decision runs its action once.** Each action tool (transfer, promise, note, callback) is entered once per decision: set a done flag in code before the route leaves the step, and have the route into the tool node test it, so a re-entry (a global node, a second pass) cannot call the tool twice (seen: two transfers on one call).
   - **Progress guard.** Detect repeated turns and follow the case's recovery or termination rules rather than looping indefinitely. When a customer corrects a read-back, apply the correction to the relevant data and repeat only the changed information.
   - **Retries:** configure retries only where the tool contract and case rules permit them. A retry must not duplicate an action that may already have succeeded.
   - **Loop guard:** prevent accidental infinite cycles in the main step or most frequently run node. Use a case-defined failure outcome when available; never invent a business outcome just to exit a loop.
   - **After a tool result:** a post-hook adds one plain instruction line (`what_to_do_next`, see `docs/tools-and-code.md`): what to say now, or which tool to call next. After a failure the line gives the exact sentence to say ("There was a technical problem. I will try once more.") and the retry rule from the brief; success wording appears only after a success result.
   - **Prompts:** short, one job per node, written as a script: "Say: ... Then ask: ... When the customer answers, ..." with the fixed sentences in quotes. Add a "do not" line only for something the brief explicitly forbids.
   - **No dead ends:** every conversation node has `max_node_turns` and a `max_turn_transition`; every path reaches the case-appropriate terminal or handoff node. Leave `agent_config` out unless the platform contract requires it.
6. Check without network: `python3 tools/validate.py out/<slot>.workflow.json inputs/openapi.json` (write `-` instead of the file name when there is no tool API file). It also checks that every tool URL is on the bank's base URL when `inputs/mock_url.txt` exists; run it as `MOCK_URL=$(cat inputs/mock_url.txt) python3 tools/validate.py ...` then. Fix every ERROR.
7. Check the arithmetic: write `out/scenarios.json` (format in `tools/codecheck.py`) with expected values you work out by hand from the brief: each band and its deadline, a weekend or holiday date, the days before and after a holiday, each edge of every time window, a phrase like "tomorrow" or "next Friday" resolved from `now`, the outcome of each path. Run `python3 tools/codecheck.py out/<slot>.workflow.json out/scenarios.json` and fix until it prints RESULT: PASS. Each scenario lists the numbers of the rules it checks in a `"rules": [...]` field; `python3 tools/rulecheck.py` must print RESULT: PASS (every rule has a home in `out/coverage.json` and most rules a scenario) before your final save. Include spoken forms in the scenarios that read dates and numbers: a date of birth with the year in words ("nineteen eighty seven" must give 1987, "two thousand and five" 2005), digits in words, an amount in words, a date such as "the third of June". Also write scenarios where extraction returns two signals at once, because one sentence often carries two (for example: the answer "no" together with a side question must start the third-party flow; a plan-request label together with a future date must lead to the promise check, not a transfer; a paid label together with a past date must close as paid; a callback time given in the third-party stage must be scheduled), and check each against what the brief says. Use at least three different `now` values: a Friday, the day before a bank holiday, and a time after the callback window has closed (plus a weekend day when the brief has callbacks).
8. Save: `python3 -c "import freya,json,sys; print(json.dumps(freya.save_workflow(sys.argv[1], json.load(open(sys.argv[2])))))" <slot> out/<slot>.workflow.json`. It prints `workflow_id` and `agent_id`. The same slot updates the same workflow. Save as soon as step 6 passes, and again after each fix. If the platform answers 503, wait a minute and try again.
9. No practice customers exist in this folder, and the phone agent is tested later by others on customers who talk like people (numbers in two parts, self-corrections, small talk, a question back, amounts and dates in words). Use the remaining time on a rule-by-rule review: write `out/coverage.json` with one entry per numbered rule of the brief naming the node or code line that carries it. Give each rule without an entry a home in the workflow, then save again.
10. Finish with one line: the `workflow_id`, the `agent_id`, and the results of the last `validate.py` and `codecheck.py` runs.

## Working rules

- Change the agent only through the file and `save_workflow`.
- Rules that must hold on every call live in code or in a route; the prompt carries the wording.
- Keep your own files in `out/`.
